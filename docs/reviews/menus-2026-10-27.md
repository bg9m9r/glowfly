# Glowfly menus: design review

Scope: every context menu, dropdown and split-button menu in `crates/glowfly-app/src/ui/`, plus the
drawn menu bar (`ui/menu_bar/`). Evidence: the code, the ~100 `*menu*.txt` text snapshots, the two
existing PNG goldens, and 33 PNGs rendered for this review (not kept in the repo; to see a
menu, add it to the pixel goldens in `ui/snapshot_check/goldens.rs`). The renders use the
Garden Dark / Garden Light palettes, which is what the view harness draws in, not Dusk/Dawn. Colours
differ slightly from the shipped default, but layout, spacing and structure are the same.

Measurements come from the renders at 1x. Row "pitch" means one item's top edge to the next one's.

---

## Summary: the findings that matter most, ranked

1. **Menu rows are the densest thing in the app (High).** egui's `set_menu_style` forces
   `button_padding = (2, 0)` inside every menu (egui 0.31 `menu.rs:77`). With 14 px text that gives
   about 19 px rows on a 23 px pitch, and label text 2 px inside the hover highlight. Graph rows are
   40 px and sidebar rows 36 px. The owner wants a roomy UI, and menus are where that is broken most
   visibly. Platform norms for mouse are a 28–32 px pitch (WinUI: 32 px minimum, 11/4/11/5 padding
   plus 2 px gaps between items).
2. **There are two different menu looks (High).** The toolbar split-button menus (Pull, Push, PR) are
   egui *popups*, not menus, so `set_menu_style` never runs on them. Their items show as filled
   "raised" buttons with 8×4 padding on a 31 px pitch (`scratch_push_menu.png`,
   `scratch_pull_menu_light.png`). Every other menu has transparent rows on a 23 px pitch. Users see
   two different components that do the same job.
3. **Destructive items look exactly like safe ones and are sometimes in the most-clicked spot
   (High).** No menu colours or separates destructive items. Some examples: the Push dropdown's first
   item is **Force push (with lease)**. The WIP file menu puts **Discard changes** second, right under
   Stage (`file_menu_commands`). **Clear recent** sits right under the recent rows with no separator.
   Hard reset, Delete…, Force delete…, Remove…, Kill terminal and Delete from remote all share the
   normal text style. Several items that ask for confirmation have no ellipsis (Force push, Clear
   recent).
4. **The repository dropdown mixes navigation with list management, and its Recent rows are not
   menu rows (High).** Each row is four separate tiny targets (☆, the path, "open", ×). Only the path
   text gets a hover pill, not the whole row. Paths show in full with no truncation. Row text starts
   at x=44 while every other item starts at x=18, and the headers start at x=16. The most frequent
   action, opening a recent repository, is at the bottom, below ten commands.
5. **Context menus are too long, with no clear priority (Medium-High).** The local branch menu has 26
   items in 8 groups (`branch_menu.png`), and the commit menu has 23 (`graph_commit_menu.png`). Win32
   guidance caps context menus at 15 items, Apple at about three groups, GNOME at 3–12 items. The
   biggest contributor is the "Preview …" twin listed after each operation (cherry-pick, rebase,
   merge, drop, reset). Runs of 3–4 disabled items in a row (Reword, Squash, Drop, Preview drop) add
   noise without helping.
6. **"Current choice" and toggle state are drawn five different ways (Medium).** These are: a "✔ "
   glyph prefixed to the text, which shifts the label right (Color submenus, tab colour, branch
   picker); a painted ✓ in a real leading column (PR filter menu, the only one that is right);
   check-box widgets (View menu check items); a second, differently placed check-box (View's diff
   toggles, 2 px off); and radio widgets (Diff layout, Theme). Labels in one menu start at three
   different x positions (`menu_bar_view_theme.png`).
7. **Keyboard support stops at the menu bar (Medium).** `menu_bar/nav.rs` keeps arrow keys inside
   the menu-bar menus. No context menu or dropdown uses it, so arrows inside them follow egui's
   default and can move focus to widgets *behind* the menu (nav.rs documents this). No list can
   open its context menu from the keyboard (Shift+F10 / the Menu key), and there's no typeahead.
8. **Group headers, separators and widths follow no system (Medium-Low).** Headers come in three
   styles (semibold body title, weak 14 px label, weak 12 px label). Single-item groups are common.
   Menus have no minimum width (the terminal menu is about 76 px wide). Labels that include branch
   names are never truncated, so a long current-branch name widens the whole menu.

What already works well and should stay:

- Disabled items say why: a greyed label, an info mark, and the reason in a tooltip, under the item on
  keyboard focus, and in the accessible description (`widgets/menu_reason.rs`).
- Row menus open *below* the row so the row stays visible, and flip above it near the bottom edge
  (`widgets/row_menu.rs`).
- Object headers ("search", "Search results page 222c0ad") tell you what the menu acts on.
- egui's submenu "moving towards" triangle keeps diagonal moves into a submenu from closing it.

## Principles (research distilled into a checklist)

| # | Principle | Source |
|---|---|---|
| P1 | Put the most important or frequent items first; people scan from the top. In a dropdown, put frequent items nearest the trigger (Fitts's law). | Apple HIG Menus; NN/g "Menu-Design Checklist" #16 (2024) |
| P2 | Group related items with separators. Groups of **7 or fewer**; context menus at most **15 items**; Apple says no more than about **3 groups** in a context menu; GNOME says **3–12 items** per menu. | Win32 UX Guide "Menus"; Apple HIG Context menus; GNOME HIG Menus |
| P3 | Context menu order: primary commands (bold default) → secondary → transfer (Copy…) → object settings → object commands (Delete, Rename) → Properties. | Win32 UX Guide "Menus" |
| P4 | Destructive items go **at the end**, set apart, marked as destructive (red text). Items that ask for more input, **including a confirmation**, end in an ellipsis; items that open submenus never do. | Apple HIG Context menus & Pull-down buttons; Win32 UX Guide "Using ellipses" |
| P5 | Use submenus sparingly, **one level**, 3–6 items; use one when **three or more items start with the same word**. Never bury frequent items in a submenu. | Apple HIG Menus; Win32 UX Guide; GNOME HIG |
| P6 | Unavailable items: the menu bar keeps a stable set and *disables*. In context menus, Apple says **hide** (2023 change), and Win32 says remove unless the user reasonably expects the item (Copy/Paste, a pair's other half). Rule of thumb: disable when the user can make it available, hide when they can't. | Apple HIG Context menus / The menu bar; Win32 UX Guide; Raymond Chen, "When do you disable an option and when do you remove it?" |
| P7 | Icons: sparingly and with purpose. **All items in a group or none** (Apple). WinUI says only where an icon is standard or illustrative, 16×16. Labels always stay. | Apple HIG Menus; WinUI "Menu flyout"; NN/g "Icon Usability" (2014) |
| P8 | Shortcuts: Apple and Win32 say **show them in main menus, not in context menus**. WinUI does show accelerator text in any flyout, as a right-aligned caption 24 px from the label. | Apple HIG Context menus; Win32 UX Guide; WinUI `MenuFlyout_themeresources.xaml` |
| P9 | Toggles use a checkmark; mutually exclusive options use a bullet/radio, at least two per group, between separators. Don't mix actions, checks and radios in one group. | Win32 UX Guide "Bullets and checkmarks"; GNOME HIG |
| P10 | Hover-revealed content: show feedback within **0.1 s**, open after the pointer rests **0.3–0.5 s**, and keep it open until the pointer has been away **> 0.5 s**. Windows' submenu default is **400 ms** (`MenuShowDelay`). | NN/g "Timing Guidelines for Exposing Hidden Content" (2015); .NET `SystemParameters.MenuShowDelay` |
| P11 | Mouse-sized rows on Windows: **32 px minimum** item height, padding 11,4,11,5 (touch: 11,8,11,9), 4 px side and 2 px vertical margin around each item's highlight, 1 px separators, a 28 px placeholder column for check/icon, a 12 px chevron 24 px from the text. | WinUI `MenuFlyout_themeresources.xaml` (`MenuFlyoutThemeMinHeight`, `MenuFlyoutItemThemePaddingNarrow`, `MenuFlyoutItemMargin`, `MenuFlyoutItemPlaceholderThemeThickness`) |
| P12 | Menus must work by keyboard: arrows, Enter/Space, Esc, Right/Left for submenus, access keys, and focus trapped in the menu until dismissed. Context menus need a keyboard trigger. | Win32 UX Guide "Access keys"; WinUI "Light dismiss"; NN/g "Designing Effective Contextual Menus: 10 Guidelines" #10 (2025) |
| P13 | Context menus hold contextual, secondary actions for the clicked object only. Don't mix global and object actions. Don't make any command reachable *only* through a context menu. | NN/g "10 Guidelines" #1, #4 (2025); Win32 UX Guide; Apple HIG |
| P14 | Labels: verb-first, specific, no articles; title case on macOS, sentence case on Windows. | Apple HIG Menus; Win32 UX Guide "Labels" |

### Where the platforms disagree, and what Glowfly should do

- **Hide or disable in context menus.** Apple now says hide, Win32 says remove with exceptions, and
  Glowfly disables with a reason everywhere. **Keep disable-with-reason** for items the user can
  unblock (Push, Cherry-pick, Rebase). The reasons are one of Glowfly's best features. **Hide**
  items that can't apply to this kind of object or state (Glowfly already hides Unset upstream
  when there is none). **Collapse runs** of items blocked for the same reason into one row (see
  the commit menu).
- **Shortcuts in context menus.** Apple and Win32 say no, WinUI shows them. The menu bar is
  optional in Glowfly and often hidden, so context menus are where people meet commands. **Show
  them**, in the weak caption style, only for items with a real app binding. This also covers the
  idea already in `docs/ideas/history-and-graph.md` (keys on Reword/Squash/Drop).
- **Capitalisation.** Glowfly uses sentence case on every OS, which matches Windows and GNOME.
  Keep it. Switching to title case only on macOS would make translations harder.
- **Row height.** Windows mouse is 32 px, macOS native is about 22 px, GNOME popovers about 32 px,
  Material is touch-first. Glowfly is "comfortable by default", so **target the Windows/GNOME 32 px
  pitch on all three OSes**, with a 24–26 px compact option.
- **Destructive colour.** Apple and Material use red text. Windows desktop menus don't. **Use the
  `danger` token on the label** on all platforms: Glowfly draws its own menus everywhere, and
  consistency inside the app matters more than mimicking Win32.

## System-wide findings

### S1. Row metrics (High)

- **What happens now:** `theme/mod.rs` sets `button_padding = (8, 4)` and `item_spacing = (8, 4)`.
  egui's `menu_popup` then calls `set_menu_style`, which overrides padding to **(2, 0)** inside every
  `context_menu`, `menu_button` and `bar_menu`. Rows end up `max(interact_size.y=18, text≈19)` tall
  on a 23 px pitch (`graph_commit_menu.png`, rows at y=252, 275, 298…). The hover pill has `MD` (6 px)
  corners, but the text sits **2 px** inside it ("Color" row in `branch_colour_submenu.png`). The
  frame margin is egui's 6 px.
- **Why it matters:** this is the opposite of the comfortable-UI preference. At 23 px a 26-item menu
  fits on screen, which is the only upside, and it hides the length problem (S5) rather than fixing
  it.
- **Fix:** restyle menus *after* egui does. See the spec.

### S2. Two menu components (High)

- Split-button carets (`toolbar_menus.rs::split`) use `egui::popup::popup_below_widget`. Popups
  don't get `set_menu_style`, so items keep the 8×4 padding *and* `widgets.inactive.weak_bg_fill =
  raised`. The enabled item draws as a filled button and disabled ones don't, so in
  `scratch_pull_menu_light.png` "Fetch all" looks pressed or selected. The pitch is 31 px against 23
  px everywhere else, and `ui.close_menu()` does nothing in a popup (closing relies on
  `CloseOnClick`).
- **Fix:** either open these with the same `menu_anchor::menu_below` mechanism the pickers use, or
  wrap the popup contents in the shared menu style (spec §1). Same component, same look.

### S3. Columns: state, label, shortcut, chevron, reason (Medium)

- **No leading column.** Check and current-choice state is drawn five ways (Summary #6). The "✔ "
  prefix approach (`branch_colour_menu.rs::checked`, tab colours, `toolbar_pickers.rs` branch list)
  moves the checked label about 18 px right of its neighbours (`branch_colour_submenu.png`:
  "Automatic" at x=507, "Rose" at x=489).
- **Shortcut column.** It is right-aligned and weak, which is correct, but it only exists in the
  menu bar and the tab menu. On a blocked item the info mark sits *between* label and shortcut,
  offset by that row's own shortcut width (`menu_reason.rs::blocked_item`, `right_inset = pad +
  key_room`), so info marks don't line up across rows with different key widths ("Reopen closed
  tab ⓘ Ctrl+Shift+T" in `menu_bar_file.png`).
- **Chevron.** egui's small filled ⏵ triangle at the far right. It works, but it's a different glyph
  from the app's painted chevrons (`widgets::chevron`) and has no reserved room. Items with a
  shortcut and a submenu would collide (none today).
- **Setup suffix.** "Set up…" follows the label at `SUFFIX_GAP`, so it starts at a different x on
  every row (`file_menu_wip_conflicted.png`).

### S4. Destructive and confirming items (High)

- No destructive styling anywhere. `Msg::confirm_danger` is used for at least: branch Delete / Force
  delete / Delete with remote, Force push, hard reset, discard, stash drop, worktree and submodule
  remove, Clear recent.
- Placement is inconsistent. Branch, tag and stash menus put Delete last (good). The Push dropdown
  puts Force push **first**. The WIP file menu has **Discard changes second**. In the repo dropdown,
  Clear recent sits right under the rows. The terminal "more" menu has Kill terminal next to Rename
  terminal.
- Ellipsis gaps: items that open a confirmation but have no "…": *Force push (with lease)*, *Clear
  recent*, *Discard changes* (check its confirm), *Kill terminal* if it asks, and *Delete from remote*
  as a submenu title (correctly has none: its children do).

### S5. Length, grouping and the "Preview" twins (Medium-High)

- Local branch: 26 items / 8 groups. Remote branch: 19. Commit: 23 plus Copy and Reset submenus.
  Multi-selection: about 10. Every menu over 15 breaks P2.
- The **Preview …** items add 5–6 rows to the branch and commit menus, and each one doubles its
  operation's row. They are a modifier on an operation, not separate commands. Options, in order of
  preference:
  1. One **"Preview before running"** check item, or a setting, so the operation item opens the
     preview when it's on.
  2. Show the preview item only while **Alt/Option** is held (Apple's "dynamic items", menu bar only
     by their rule, but harmless here).
  3. A split row: the operation, plus a small trailing "preview" icon button inside the same row
     (WinUI's `SplitMenuFlyoutItem` pattern).
- **Single-item groups** waste separators: "Create pull request…" (branch), "Compare with working
  directory" (commit), "Copy" (branch, tag), "Refresh" (View). GNOME says to put single items at the
  top or bottom, or merge them into a neighbouring group.
- **Runs of disabled items.** For a commit off the current branch, Reword / Squash / Drop / Preview
  drop are all disabled for the same reason. Collapse them into one disabled row "Edit this commit"
  with the reason, or hide the group. For a branch with no host, "Create pull request…" is disabled
  in its own group: keep it (it teaches) but merge the group.

### S6. Group headers and object headers (Medium-Low)

- **Object header** (`common.rs::header`): semibold body, wraps at 320, separator after. It's good,
  and keeps commit, branch and tag menus anchored to their object.
- **Section headers** come in three styles. `repo_list.rs::header` is `ui.label` weak at **14 px**, 2
  px left of item text. `menu_bar/draw.rs` Heading is **12 px** weak with a 4 px top gap.
  `forge_filter_menu` "Saved filters" is 12 px weak. The sidebar section headers elsewhere are
  semibold. One style is needed (spec §5).
- Headers follow a separator *and* are headers, which double-marks a group. With a header, drop the
  separator line and use 8 px of space.

### S7. Width and truncation (Medium)

- No minimum width on context menus (terminal ≈ 76 px, `graph_label_menu_many.png` ≈ 124 px), while
  dropdowns set ad-hoc minimums (200, 220, 230, 240, 250, 260) in five places.
- Item text never wraps (`TextWrapMode::Extend`, correctly). But interpolated names are never
  shortened, so a long current branch makes "Interactive rebase todo/very-long-branch-name onto this
  branch…" set the menu's width. The header caps at 320 but items don't.
- Paths: repo rows show the full native path (`C:\work\api-server`). Real paths
  (`C:\Users\ada\source\repos\client\project-name`) will make this menu very wide, and the part
  that identifies the repo (its folder name) is at the far end.

### S8. Keyboard (Medium)

- The menu bar has proper navigation (`menu_bar/nav.rs`: Up/Down stay in the menu, Left/Right
  switch menus, the first item takes focus on keyboard open, focus kept inside).
- Context menus and dropdowns don't. No keyboard way to open a row's context menu (Shift+F10 /
  Menu key), no Home/End, no typeahead, no wrap from last item to first. Submenus open only on hover
  (egui), so a keyboard user can't reach Copy ▸, Color ▸, Push to ▸.
- Focus doesn't return to the row after the menu closes.

### S9. Placement (Low)

- Row menus: below the row, flip above (`row_menu.rs`). Good.
- Dropdowns: `menu_anchor::below` lines the first item's text up with the button, which is good.
  Split popups use `fixed_pos` at the caret's left-bottom, so the Push menu's left edge is 6 px
  right of the button group and not lined up with anything.
- Submenus: egui positions them to the right and clamps to the screen, but doesn't **flip to the
  left**. Near the right edge the submenu ends up over its parent (Theme submenu in
  `menu_bar_view_theme.png` is shifted up; the Color submenu in `branch_colour_submenu.png` is
  pushed up to y=460 for a parent row at y=714, far from the pointer).
- Submenus open instantly on hover (egui). Sweeping down past "Color" or "Copy" opens and closes
  flyouts on the way, which goes against P10.

### S10. Consistency between menus (Medium)

- The same command has different names: "Copy path" vs "Copy URL" vs "Copy link" vs "Copy #12" vs
  "Copy card link" (fine), but "Open folder" (worktree) vs "Show in Explorer" (file) vs the toolbar's
  "Folder" for the same OS action.
- Copy is a submenu in commit/branch/tag menus but flat in file, blame, history and worktree menus.
  That's acceptable (submenu only at ≥3 items), but then Copy ▸ with two items in the branch menu
  (name, link) breaks the ≥3 rule.
- Hide in graph / Show only this / Color: same order everywhere, which is good.

## Scenario by scenario

### 1. Repository dropdown (toolbar "Repository" picker)

Files: `ui/toolbar_menus.rs::repo_menu`, `ui/repo_menu.rs`, `ui/repo_list.rs::{menu_sections,row}`.
Snapshots: `repo_menu`, `repo_menu_actions`, `repo_menu_sync`. Renders: `scratch_repo_menu_dark.png`
and `scratch_repo_menu_light.png` (api-server row hovered), `repo_menu_sync.png`.

Today: Open repository… / Clone repository… / New repository… ┃ Dashboard / Find repositories in
folders… / Open all favorites in tabs / Fetch or pull repositories ▸ / Remove missing entry (1) / Add
this repository to favorites ┃ *Favorites* ★ path ┃ *Recent* ☆ path [open] × … / Clear recent.

Good:
- The fixed slot keeps the picker from jumping.
- The menu's first item text lines up with the button.
- The star toggle and × don't close the menu, so you can tidy several rows at once.
- A missing repo is greyed with a "not found" tooltip.

Problems:
- **(High) Navigation and list management in one flat menu.** Ten commands of four kinds come
  before the list: create/obtain (Open, Clone, New), workspace (Dashboard, Find, Open all),
  batch-sync (Fetch/pull ▸), list hygiene (Remove missing, Add to favorites). The main job of a
  repository picker is *switching*. P1 and NN/g #16 both say the frequent target belongs next to
  the trigger. Here it sits at the bottom, roughly 300 px from it.
- **(High) Recent rows aren't menu items.** Each row is `ui.horizontal` with four widgets:
  `small_icon` ☆ (about 16 px target), a `Button` path whose hover pill covers only its text, a weak
  12 px "open" label (clickable, PointingHand cursor), and a 16 px ×. The row as a whole has no
  hover, no focus and no accessible row node. "open" and the path do the same thing (switch to the
  tab), so there are two targets for one action, and the one labelled "open" looks like a status,
  not a button.
- **(High) Alignment.** Headers start at x=16 (a label has no button padding), item text at x=18,
  recent-row paths at x=44 (after the star), and "Clear recent" back at x=18. Four left edges in one
  menu.
- **(Medium) Path display.** Full native paths, not truncated, with the identifying part
  (the folder name) last. Two repos called `web-app` under different parents need the parent, but
  the folder name should lead.
- **(Medium) "Clear recent" is destructive** (it asks for confirmation: `repo_menu_favorites_and_recent`
  test) but has no ellipsis, isn't set apart, and sits where a user aiming for the last recent row
  will land.
- **(Medium) "Add this repository to favorites"** is a toggle written as a sentence. Its state is
  already shown by the star, which this row (the current repo) doesn't have, because the current
  repo isn't in Recent.
- **(Medium) "Remove missing entry (1)"** is list hygiene in the command group. It belongs next to
  the list, or in the Dashboard.
- **(Low) "Fetch or pull repositories ▸"** is batch work across repos. It's correctly a submenu (four
  items), but it's workspace-level and arguably belongs in the Dashboard. Keep it, but in the
  workspace group.
- **(Low) With 20+ recents** there's no filter, and the menu becomes a scroll.

Recommendation (Glowfly's own layout):

```
┌──────────────────────────────────────────────┐
│ [ Find a repository…                     ]   │  ← filter field, focused on open (type to filter)
│ FAVORITES                                     │  ← group header (spec §5)
│ ● web-app            C:\work          ★      │  ← one 32 px row: swatch · name · weak parent path
│ RECENT                                        │
│   api-server         C:\work   In a tab  ☆ × │  ← ☆ and × appear on row hover/focus only
│   old-site           C:\work   Not found ☆ × │  ← name in faint, tag shown (not only a tooltip)
│ ───────────────────────────────────────────  │
│ Open repository…                    Ctrl+O   │
│ Clone repository…                            │
│ New repository…                              │
│ ───────────────────────────────────────────  │
│ Dashboard                                    │
│ Find repositories in folders…                │
│ Open all favorites in tabs                   │
│ Fetch or pull repositories                ›  │
│ ───────────────────────────────────────────  │
│ Remove missing entries (1)…                  │  ← list hygiene, last, with ellipsis (it asks)
│ Clear recent…                                │  ← danger colour, last
└──────────────────────────────────────────────┘
```

- Each list row is **one** menu row: the hover pill and focus ring cover the whole row, Enter or a
  click opens or switches. ☆ and × are 24×24 inline icon buttons in the row's trailing area. They
  stay hidden until the row is hovered or focused, except the filled ★ of a favorite, which always
  shows as state. The PR filter menu's saved-filter row already does this
  (`sidebar_pr_filter_menu.png`): reuse that pattern.
- Name first (body, `text`), then the parent folder (SMALL, `weak`, middle-truncated to fit, full
  path in the tooltip and accessible name). Use the same swatch slot as today.
- "In a tab" (or a small filled dot plus tooltip) replaces the clickable "open" label. The row
  itself switches to the tab.
- Mark the current repository's row (check in the state column) instead of the "Add this repository
  to favorites" sentence. The current row's ☆ toggles favorite.
- Move "Remove missing" and "Clear recent…" to the bottom group, in `danger` for Clear, both with
  ellipsis because both confirm.
- Optional: put the filter field at the top only when there are more than about 8 entries.
- File ▸ Open recent (`menu_bar_file_recent.png`) reuses `recent_submenu`. Apply the same row
  component there. Its x offsets are off the same way (header 263, path 291, Clear 265).

### 2. Branch picker (toolbar "Branch")

`toolbar_pickers.rs`, `branch_picker_menu_dots.png`.

- Good: colour dots before names match the graph.
- **(Medium)** The current branch is shown **disabled** (faint, with an info mark, "✔ main"). The
  current choice in a picker should look selected and enabled, with a check in the state column, not
  greyed as if unavailable. Clicking it can just close the menu.
- **(Medium)** No filter. Repos with 50+ branches make this a long scroll. Add the same filter field
  as the repo picker, and consider a "Remote branches ▸" group.
- **(Low)** "New branch…" after a separator is correct. Consider a shortcut hint (Ctrl+B if bound).

### 3. Graph commit menu and multi-selection menu

`ui/menus.rs::{commit_menu,multi_commit_menu}`, `graph/ref_menu.rs`. Snapshots `graph_commit_menu`,
`graph_commit_menu_copy_submenu`, `graph_commit_menu_reset_submenu`, `commit_menu_*`,
`graph_multi_menu`, `multi_commit_menu_*`, `row_menu_below_graph`.

- Good: the header (bold summary plus weak mono SHA), the reset submenu titled with the branch it
  moves, and the hint under Hard reset.
- **(High)** 23 items. Five "Preview …" twins (S5). Four consecutive disabled edit items on any
  commit off the current branch.
- **(High)** "Hard: reset files too…" is destructive and isn't marked. Inside the Reset submenu,
  "Preview reset…" comes first (fine), then Soft/Mixed/Hard. Hard should be last (it is) and in
  `danger`.
- **(Medium)** Group 2 mixes "apply this commit elsewhere" (cherry-pick, revert) with "move my branch
  onto this" (rebase ×3). Group 3 mixes reset with editing history. Suggested groups:
  1. Checkout (detached) · Create branch here… · Create tag here… · Create worktree…
  2. Cherry-pick · Revert · Rebase *main* onto this · Interactive rebase *main* onto this…
  3. Edit ▸ (Reword… Squash into parent… Drop…), or inline when available, hidden or collapsed when
     not
  4. Reset *main* to this commit ▸ · Interactive rebase from here…
  5. Compare with working directory · Create patch… · Copy ▸
  6. Commands ▸ (custom)
- **(Medium)** Shortcuts: once keys exist for reword/squash/drop/cherry-pick, show them (decision
  above).
- **(Low)** The multi-selection header "2 commits selected · Esc to clear" is good (Apple: titles only
  when they clarify, such as a count). The selection panel already lists the actions with full
  labels ("Cherry-pick 2 commits"); the menu uses the short ones. Fine.
- **(Low)** `graph_label_menu_many.png`: the chooser menu ("Branch main ▸ / Tag v0.1.0 ▸") is about
  124 px wide with no minimum. Give it the 200 px minimum and a ref-kind icon in the state column

### 4. Local branch menu (sidebar and graph chip)

## Proposed menu design spec (egui 0.31)

Every value is in points. "New token" means add it to `theme/spacing.rs` (a `menu` block) or
`theme/tokens.rs`. Keep them on the 4 px grid.

### §1 Apply one style to every menu

egui calls `set_menu_style` *before* running a menu's contents, so restyle at the top of the
contents. Add `ui/widgets/menu.rs` (or extend `ui/menus.rs`) with:

```rust
/// Call first inside every context_menu / menu_button / bar_menu / split popup.
pub fn style(ui: &mut egui::Ui) {
    let s = ui.spacing_mut();
    s.button_padding = vec2(menu::PAD_X, 0.0);     // height comes from interact_size
    s.interact_size.y = menu::ROW_H;               // 28 (comfortable) / 22 (compact)
    s.item_spacing = vec2(menu::GAP_X, menu::ROW_GAP);
    ui.set_min_width(menu::MIN_W);
    ui.set_max_width(menu::MAX_W);
    // Popups (split buttons) don't get egui's menu style: make inactive rows transparent here too.
    ui.visuals_mut().widgets.inactive.weak_bg_fill = Color32::TRANSPARENT;
    ui.visuals_mut().widgets.inactive.bg_stroke = Stroke::NONE;
}
```

Then:
- Set `style.spacing.menu_margin = Margin::same(menu::FRAME_PAD)` in `theme/mod.rs::apply_style`.
- Route `menu_item*`, `reason::menu_button`, `branch_dot::menu_row` and `ui.menu_button` through
  this style (a wrapper `menu::submenu(ui, label, |ui| …)` that calls `style` inside).
- Add a `tests/layering.rs`-style hygiene check that `ui.menu_button(` and `.context_menu(` are only
  called from the wrapper.

### §2 Metrics

| Token (new) | Comfortable (default) | Compact (opt-in) | Notes |
|---|---|---|---|
| `menu::ROW_H` | **28** | 22 | the hover pill's height |
| `menu::ROW_GAP` | **2** | 2 | space between pills, so the pitch is **30 / 24** |
| `menu::PAD_X` | **12** | 8 | text inset from the pill edge (WinUI 11) |
| `menu::FRAME_PAD` | **4** | 4 | frame inner margin, so pills sit 4 from the edge |
| pill corners | `radius::SM` (4) | `radius::SM` | the frame is `radius::around(SM, 4)` = 8 = `LG` (nested-radius rule) |
| frame corners | `radius::LG` (8) | `LG` | unchanged |
| `menu::MIN_W` | **200** (context), dropdowns: max(200, anchor width) | 180 | |
| `menu::MAX_W` | **380** | 340 | interpolated names truncate to fit (§8) |
| text | `type_scale::BODY` 14 | 14 | |
| shortcut / suffix | `SMALL` 12, `color::weak()` | same | |

Comfortable gives a 30 px pitch with 4 px top and bottom padding: close to WinUI's mouse layout and
GNOME's. Compact gives 24 px, which is today's density with proper side padding. Hook it to the
existing compact preference if there is one, otherwise a new `settings.menu_density`.

### §3 Columns (per menu, laid out left to right)

```
| 4 | 12 | [state 16] 8 | label …………… | ≥24 | [reason 16] 8 | [shortcut, right-aligned] | 8 [chevron 12] | 12 | 4 |
```

- **State column** (`menu::STATE_W = 16`, gap 8): reserved for **all** rows of a menu when **any**
  row has a check, radio, swatch or icon (WinUI's placeholder, Apple's "all or none in a group").
  It holds a painted ✓ (`Icon::Check`, `color::accent()` or `text()`), a radio dot (6 px filled
  circle), a branch or repo swatch (`branch_dot`, `repo_swatch`), or an icon (16 px). Without one,
  the label starts at 12 + 4 = 16 from the frame edge. With one, 16 + 16 + 8 = 40.
- **Label:** never wraps. Interpolated names middle-truncate (§8).
- **Reason slot** (`INFO_W` 16): a fixed slot left of the shortcut column, the same x on every row,
  not offset by that row's key width (fixes S3).
- **Shortcut column:** right-aligned to a common x, `SMALL` weak. Shown for items with an app
  binding, in menu bar and context menus alike. "Set up…" suffixes go here too.
- **Chevron:** the painted `widgets::chevron` at 12 px, `color::weak()` (`text()` while the row is
  hovered or open), in a reserved 12 px slot. Menus with any submenu row reserve it on all rows, so
  shortcut columns stay aligned (Blender/GNOME practice).

### §4 Separators

- 1 px line in `color::border()` (or `overlay_edge()` if the border is too strong on the overlay),
  spanning the frame's inner width (pill edges), with **4 px** above and below. That's 9 px total,
  which works out to the 2 px row gaps on each side plus the line.
- Never two in a row. No separator directly before a group header (§5) or as the first or last
  child.

### §5 Group header (one style everywhere)

- Text: `SMALL` (12) **semibold** via `type_scale::strong(ui, SMALL)`, `color::weak()`, sentence
  case, not uppercase (no letter-spacing support, and translations).
- Lined up with the **label column** (x = 16, or 40 with a state column), not with the pill edge.
- 8 px above (4 when it's the first child), 2 px below, height 20. Not focusable, `selectable(false)`,
  given a `Role::Group`/heading node for screen readers.
- A header **replaces** the separator for its group.
- Replaces `repo_list::header`, `menu_bar::draw` `Entry::Heading` and the forge filter's "Saved
  filters" label.

The **object header** (`common::menu_header` and friends) stays as it is (semibold `BODY`, wraps at
`MENU_HEADER_W` 320, weak mono SHA), with a separator after. Lay it out at the label x and give it 6
px top and 8 px bottom padding.

### §6 States

| State | Label | Background | Other |
|---|---|---|---|
| rest | `text` | none | |
| hover / keyboard focus | `text` | `hover_on(overlay)` pill (today's `widgets.hovered.weak_bg_fill`) | focus also gets `focus_ring_inset` (as `menu_reason::paint_focus`) |
| pressed | `text` | `selected` | |
| submenu open | `text` | the hover pill stays while its submenu is open (egui's `open` state) | chevron in `text` |
| disabled with reason | `faint` | hover pill only on hover/focus, no click | info mark in the reason slot (`weak`, `text` when lit); reason in tooltip after 300 ms, and inline under the row on keyboard focus (as today) |
| current choice | `text` | none | ✓ in the state column |
| **destructive** | `color::danger()` | hover pill = `hover_on(overlay)` tinted 12% toward `danger` (new token `danger_hover`) | always in the **last group**; "…" when it confirms |
| setup needed | `text` + "Set up…" in the shortcut column | normal | as today |

Contrast check: `danger` on `overlay()` must reach 4.5:1 in every built-in theme. Add it to
`theme/contrast.rs`'s pairs.

### §7 Submenus and hover intent

- **Open delay 250 ms** while the pointer rests on the row (between NN/g's 0.3–0.5 s and Windows'
  400 ms; Glowfly's menus are short enough that 250 ms doesn't feel sluggish). Opens **immediately**
  on click, Enter, Space or Right arrow.
- **Close grace 400 ms** after the pointer leaves both the row and the submenu, on top of egui's
  existing "moving towards the submenu" triangle (`menu.rs::moving_towards_current_submenu`).
- egui 0.31 opens on hover with no delay. Implement the delay in the `menu::submenu` wrapper by
  keeping a hover-start time in temp data and drawing a non-opening row until it elapses. That's the
  same "drawn as a disabled item" trick `menu_bar/items.rs::submenu_if` already uses.
- Placement: the submenu's first row lines up with its parent row (egui does this). When it doesn't
  fit on the right, **flip to the left** of the parent. When it doesn't fit vertically, shift it up
  only as much as needed and keep it at least 8 px from the window edge.
- One level only (P5). Today's maximum is one, so keep it that way.

### §8 Width, truncation and paths

- Width = clamp(widest row, `MIN_W`, `MAX_W`).
- **Interpolated names** (branches, remotes, tags, SHAs inside labels like "Rebase *main* onto this
  branch"): middle-truncate the *name part only* with `widgets::truncate::cut_middle_in` to
  `menu::NAME_MAX = 28` characters (or by width: keep the label within `MAX_W`). The full label goes
  in the tooltip and accessible name. This keeps the verb visible.
- **Paths:** show the folder name (BODY, `text`) and the parent path (SMALL, `weak`), with the parent
  middle-truncated to fill the remaining width: `C:\Users\…\client`. The full native path goes in the
  tooltip and accessible name.
- **Object header:** keeps wrapping at 320 (it's the one place where the full name matters).

### §9 Keyboard

Generalise `menu_bar/nav.rs` into `ui/menu_keys.rs` and apply it in the §1 wrapper to every menu:

- Up/Down move between focusable rows, skipping headers and separators, **wrapping** at the ends.
  Home/End go to the first and last row. Disabled rows take focus (they explain themselves), as
  today.
- Enter/Space activates. Right opens a submenu and focuses its first row. Left or Esc closes one
  level. Esc from the root closes the menu and **returns focus to the invoking row or button**.
- **Typeahead:** a printable key jumps to the next row whose label starts with it (case-folded,
  using the label in the active language).
- **Opening from the keyboard:** Shift+F10 and the Menu key (where egui reports it; otherwise
  Shift+F10 alone) open the focused or selected row's context menu, anchored below that row with
  `row_menu` placement, first item focused. Dropdown buttons open on Enter, Space or Alt+Down.
- Focus is trapped in the open menu (WinUI light dismiss); arrows never reach widgets behind it.

### §10 Ordering and content rules (for authors)

1. Object header (when the menu acts on one object).
2. Primary group: the default action first (Checkout, Open, Stage). Consider **semibold** for the
   default, the one the row's double-click runs (Win32).
3. Secondary actions, grouped by intent. 7 or fewer per group.
4. Transfer: Copy ▸ (submenu only with 3 or more items).
5. Object settings: Hide in graph, Show only this, Color ▸.
6. Commands ▸ (custom).
7. Destructive group, last, `danger`.

Also:
- At most about 15 items per context menu.
- Hide what can't apply. Disable with a reason what the user can unblock. Collapse three or more
  rows blocked for the same reason.
- "…" when the item asks for anything, including confirmation. Never on submenu titles.
